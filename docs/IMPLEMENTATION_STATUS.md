## إضافة الجمهور المستهدف

1. تختلف بنية التقرير وترتيب الأقسام والإجراءات حسب الجمهور (CFO، مجلس، تشغيل، مبيعات أو قطاع)، وليس العنوان وحده.
2. يبقى الرقم المالي ومعادلته ووحدته ومصدره واحدًا مهما اختلف الجمهور.
3. لا يؤدي `audience` إلى زيادة صلاحيات من يقرأ التقرير أو ينشئه؛ المجلس لا يقرأ المصادر الخام والمسودات.
4. تحفظ قيمة الجمهور وأقسامه داخل لقطة التقرير المعتمد ولا تتغير بتغيير إعداد العرض لاحقًا.
5. تحليل المبيعات/القطاع يمتنع صراحة عن التفصيل غير المتاح، ولا يخترع خطوط أعمال أو عملاء أو مبيعات مناطق من قوائم مجمعة.

اختبرت هذه الإضافة فعليًا بعد تنفيذ `shared/audiences.json`: نجح AUDIENCE-01 وAUDIENCE-02 في اختلاف الأقسام وثبات الأرقام وطلبات البيانات الناقصة وثبات لقطة الجمهور وعدم تصعيد الصلاحيات. لم تختبر جودة الصياغة مع مستخدمين من الجمهور الحقيقي.

## سجل التنفيذ

آخر تشغيل API فعلي على `http://127.0.0.1:4317`، بمحرك Python الحقيقي وبيانات محلية معزولة: **36 فحصًا ناجحًا، صفر إخفاق، صفر فحص متعذر**. سجل الأدلة: `verification-evidence/api-mujvs2kg.json`؛ الربط المحدود بالمتطلبات: `verification-evidence/feature-coverage.json`.

أعيد تنفيذ 28 اختبار محرك مستقلًا، ونجحت رحلتا المتصفح: 7 خطوات رفع ومراجعة واعتماد مستقل ونشر للمجلس، و7 خطوات مؤشر/مصدر وسيناريو وإجراء/دليل/إغلاق/منفعة. تفاصيل نتائج التخطيط والوصول ووقت إعادة الفحص في `QA_REPORT_AR.md`؛ لا تساوي الفحوص الآلية شهادة WCAG.

عولجت وأعيد اختبارها: ظهور الاستنتاج المرفوض، اعتماد مسودة قديمة، اختلاف سياسة الحساب، تكرار رفع المصدر، التاريخ/الملف التالف، روابط أدلة التقارير، حالات الصيغ غير المحسومة، مقارنة عملات غير متجانسة، عرض الوحدات النقدية/الفجوات، تركيز قائمة الجوال، وعرض المنافع وتاريخ الإجراء. هذه نتائج تطوير محلي وليست اختبار اختراق شاملًا أو إثبات صلاحية تجارية.
